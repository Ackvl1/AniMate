Hook + Tool-Use Loop

# animate/agent/agent.py（实际代码）
# Phase 1：预处理
for cap in active_caps:     # ← 非 deferred 的 Capability
    instr = cap.instructions(ctx)
    if instr: ctx.system_prompt_parts.append(instr)
    cap.before_llm(ctx)

messages = build_messages(ctx)  # system + history + user

# Phase 2：LLM + Tool 循环（最多 5 轮）
while tool_round < 5:
    for event in llm.chat_stream(messages, tools):
        if event["type"] == "delta":
            yield Chunk(delta=event["content"])
        elif event["type"] == "tool_call":
            buffer[idx] = event           # 累积
        elif event["type"] == "done":
            break
    if buffer:                        # 有 tool_call
        execute each tool → append to messages
        continue                     # 回 LLM
    break                           # 没 tool_call → 结束

# Phase 3：后处理
for cap in reversed(active_caps):  # ← 逆序
    text = cap.after_llm(ctx, text)

final_text, emotion, gesture = _parse_structured(text)
yield Chunk(text, emotion, gesture, is_final=True)
流式输出 工具调用 前后钩子 结构化输出 适合角色扮演

▌项目场景推荐

推荐哪个场景用哪个

Pipeline 简单对话机器人、固定流程客服、无工具需求
Hook+Loop 角色扮演 Agent（你的 AniMate）
人格+RAG+情绪+工具+结构化输出，功能全盖住
Graph 复杂推理、代码生成、多步规划、多Agent协作

AniMate 结论

✓ Hook + Tool-Use Loop 是最优解

为什么不选另外两个：
• Pipeline 太简陋 — 没有工具调用、没有流式、没有后处理
• Graph 太复杂 — 角色扮演是固定流程，并行/条件路由用不上

下一步扩展方向：
• 继续加 Capability 内置实现（Persona/Retrieval 已经写了）
• 需要 MCP 工具时 → 加 MCPClient，对接 ToolRegistry
• 需要复杂分支时 → 可以 Graph 里套一个 Hook 节点，Hook 里调 Graph 子图
  两者不是互斥的，可以混用

Pipeline ← 简单但局限  ·  Hook + Tool-Use Loop ← 你的项目在这  ·  Graph → 灵活但复杂

前版把"Capability"包装成标准架构是错的。修正为：实际就是 Hook 模式 + Tool-Use Loop。
